What it is

Lutz Hühnken writes on software architecture and sells consulting in this area. The post covers events published between services, not internal events for event sourcing. It asks what an event should contain.

What it says

  • The post says events in event-driven systems both trigger actions and carry data.
  • The post says there is no agreement on how much data an event should hold.
  • Wide events carry most of an entity's data. They are also called fat events or state events.
  • The developer view favours distinct event types, such as SeatSelected then PaymentReceived then TicketIssued.
  • The data engineer view favours one event type per stream, easing table ingestion.
  • Wide events suit data warehouse feeds, bootstrapping new services, and keeping local copies of data.
  • The author prefers wide events that name their reason in the event or header.

What evidence it gives

The post offers argument and one worked example, a cinema ticket flow. It names Kafka schema registry strategies for each view. It gives no data, benchmark or case study.

Interests and limits

The author offers consulting and training on event design, and says so at the end. The advice is one practitioner's approach. The post invites readers to share their own approach in comments. It does not test either view.
