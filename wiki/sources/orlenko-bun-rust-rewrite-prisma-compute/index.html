We put Bun's Rust rewrite in production on Prisma Compute

What it is

Alexey Orlenko writes for the Prisma blog, part two of a series on Prisma Compute. The post explains why Compute runs on the Rust rewrite of Bun. It sets out what Compute demands of a runtime and what broke on stable Bun.

What it says

  • The post says Compute launched its beta on the Rust rewrite, expected as Bun 1.4.
  • On stable Bun 1.3.14, a repeated S3 read test crossed 900 MiB around iteration 96.
  • On canary, the same test stayed flat over 4096 iterations, near 118 MiB.
  • Earlier Bun versions deadlocked the SQL pool after restores. The post reports the pool recovered on the Rust rewrite.
  • The post rejects a private patched fork of Bun as a foundation for the platform.
  • The post credits Rust's ownership model with removing a class of manual cleanup mistakes.
  • The post concludes modestly that, under Compute's conditions, the rewrite behaved better than stable Bun.

What evidence it gives

The post cites a public Bun issue, number 29083. Its small repro reads an S3 object repeatedly. It reports memory figures for both builds. The pool result rests on Prisma's own testing, with no numbers given.

Interests and limits

Prisma sells Compute, so the company has an interest in the choice looking sound. The post says it is not claiming every pool failure is fixed. It tests one workload and gives no independent replication. A later note says Compute became generally available in August 2026. The post says the translated code still needs review and its unsafe code needs auditing.
