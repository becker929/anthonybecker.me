Summaries that point down

The chat brief says every unit of agent work closes to a one-line summary, and that a parent's summary is built from its children's. Today those lines are templates. This is a design for the model-written ones, using the cheapest model of whichever engine you picked.

Written by Claude Fable 5.2Addressed to AnthonyWednesday 18 November 2026, 00:16 UTC (Tuesday 16:16 Pacific)

Summary

  • Keep the template line on every row. It carries the facts: counts, errors, status.
  • Add one model-written line that says what the work was for and what it found.
  • Write it bottom-up. A step is summarized from its tool calls. A turn is summarized from its step lines only. A session from its turn lines only.
  • Use the cheapest model of the engine that ran the turn: the Flash-Lite tier for Gemini, Haiku for Claude Code.
  • Do it on the server, once, and store the line as an event. Every device then replays the same line.
  • A summary that fails a check is dropped. The template line is always there, so nothing waits on the model.
  • Nothing here is built yet. Four decisions are yours; they are at the end.

What exists today

Zpkt web already folds work into four levels. Every line is a template built in code, so it cannot misstate anything. It also cannot say why.

The brief asked for this split: templates at the tool level, model summaries from the step level up. It also named the risk. A model-written summary may misstate what happened.

The design in one picture

Each level keeps its template line and gains a purpose line. Arrows show what each purpose line is written from.

session   "Kick tuning for HW002"                 ← from turn lines
└ turn    "Shortened the kick decay; compare failed" ← from step and subagent lines
  ├ step  "Measured the kick: the sub rings long"   ← from its tool calls
  │  ├ ran ears analyze renders/mix-a.wav          (template)
  │  └ read kick.json                              (template)
  ├ step  "Set decay to 240 ms; one edit failed first"
  └ agent "Kick tuner: mix-c.wav is missing"        ← from its steps and report

A summary only ever reads one level down. That is the rule from the brief, and it is what makes each line checkable: every claim points at a child you can open.

Two lines, two jobs

The template line and the purpose line never share a job.

  • Template line: facts. How many calls, which kinds, how many errors, done or failed. Code writes it. It stays on every row.
  • Purpose line: meaning. What the work was for and what it found, in twelve words or fewer. The model writes it.

The purpose line may not state counts or status. Those come from code. So if the model is wrong, it is wrong about meaning, next to facts that are right. "Problems never collapse" keeps holding, because problems live in the template line.

On a row, the purpose line is the title and the template line sits under it, smaller. A row with no purpose line looks exactly as it does today.

Which model writes it

The engine you picked for the turn also writes that turn's summaries. Your work then goes to one provider per turn, the one you chose.

EngineSummary modelHow it is calledSpeed
Gemini CLIFlash-Lite tierDirect API call from the server, with the key it already holdsAbout a second, I expect
Claude CodeHaikuA one-shot claude -p --model haiku with no tools and no saved sessionSeveral seconds: the CLI has to start

Two things I have not measured: the speed column, and the cost. Both models are their provider's cheapest tier, and a step summary is small: a few hundred tokens in, about thirty out. I would log real token counts in the first build before quoting a price.

The model names live in settings, not in code. Providers rename their cheap tier often. Claude Code accepts the alias haiku, which follows the newest one.

Claude Code has no API key on your Mac, only its sign-in. So the Claude path has to go through the CLI, and it draws on the same usage limits as your turns. That is the main reason to batch.

When a summary is written

  • Step closes. It joins a queue. The queue is sent when it holds eight steps, or after five seconds, or when the turn ends.
  • Subagent finishes. Its steps are summarized like any others. Its gist is written from those lines plus its report.
  • Turn ends. The queue is flushed. Then the turn line is written from the step and subagent lines.
  • After each turn. The session title is rewritten from the turn lines.

On Claude Code, I would start with one call per turn: all the steps and the turn line in a single CLI start. Live step lines on Claude can come later if the delay is tolerable.

Some work is skipped on purpose.

  • A step with one tool call. "Ran live bounce --bars 17-24" needs no gloss.
  • A turn with no tool calls. The answer is the summary.
  • Replays. A stored line is never regenerated.
  • Anything past a per-turn cap of forty summary lines. Long turns keep templates for the rest.

What the model sees

For a step: the sentence the agent wrote just before it, each tool call's template line, and a clipped piece of each result. The first 400 and last 200 characters are enough to see what a command printed.

For a turn: your message, the step purpose lines with their template lines, and the subagent gists. No tool output at all.

For a session: the turn lines only.

The instruction is short. In outline:

You label steps of an agent's work for the person who asked for it.
For each step, write one line of at most 12 words:
what it was for and what it found.
Do not give counts. Do not say whether it succeeded.
Use only what is in the step. If you cannot tell, write "unclear".
Answer as JSON: [{"id": "...", "line": "..."}]

Keeping it honest

The brief listed unverified summaries as a known limit. Four checks run in code before a line is stored.

  • Shape. One line, twelve words or fewer, plain text.
  • Numbers. Every number in the line must appear in what the model was shown.
  • No verdicts on failures. If the step has an error, words like "fixed", "passed" or "done" drop the line.
  • No "unclear". If the model could not tell, the row keeps its template alone.

A dropped line is not retried. The template is the fallback, and it is always already on screen.

Each stored line records which children it was written from and which model wrote it. Opening the row shows those children. That is the evidence link the brief pointed to, without a second model checking the first.

You also need a way to say a line is wrong. A long press on a purpose line marks it wrong and hides it. The marks are the measure of whether this is worth keeping.

Where it lives

  • One new server module queues closed nodes, calls the model, checks the answer and appends an event.
  • One new event. { type: "summary", level, ref, line, from, model } in the session's log, beside the events it describes.
  • The work model in the page learns that event and gives the node a purpose line. Drawing code changes by a few lines.
  • A setting with three values: off, steps and turns, everything.

Because the line is an event, your phone and your laptop show the same words, and a reload costs nothing.

The staging tests gain a stand-in summarizer, so the whole path runs in a real browser without calling a model.

What this is not

It is not the agent's memory. Rule 7 of the brief, showing and editing the summary the agent works from after compaction, is a separate job. These lines are for you. The agent never reads them.

One tempting reuse: when you switch engine mid-session, hand the new engine the turn lines instead of the whole transcript. I would not do that yet. It changes what the agent knows, and a wrong line would then steer the work.

Order of work

  1. Server module, the event, the checks, and step lines on Gemini. Log tokens and delay.
  2. Turn lines and the long-press "wrong" mark.
  3. The Claude Code path, one call per turn.
  4. Session titles.
  5. After a week of real use: count the lines you marked wrong. Keep, narrow or remove.

Your decisions

  1. Which line leads? I propose the purpose line as the title, with the template under it. The other way round is safer and duller.
  2. On by default? I propose steps and turns on, session titles off until you have seen them.
  3. Is a delay fine on Claude Code? Lines would arrive a few seconds after the turn ends.
  4. Should session titles change under you? A title that tracks the work is easier to find later, and harder to recognise the next minute.

Glossary

Engine
The agent program behind the chat: Gemini CLI or Claude Code. You pick it per message.
Event
One stored line of a session's record. The page is drawn by replaying them.
Purpose line
The proposed model-written line: what a piece of work was for and what it found.
Step
A run of tool calls between two pieces of the agent's text.
Subagent
An agent the main agent starts for part of a task. It gets a brief and returns a report.
Template line
A line built by code from the calls themselves, such as "Ran 2 commands (1 error)".
Token
A piece of a word. Models read and write in tokens, and are billed by them.
Tool call
One action an agent takes, such as running a command or reading a file.
Turn
One message from you and everything the agent does in answer.
