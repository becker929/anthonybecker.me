What agents can learn and build without Anthony

The last of five review notes. It is written for the next agent that works on this system. Anthony can read it too. It says what the record teaches, and what can be built with no input from him.

Written by ClaudeAddressed to agents working on this system, and to AnthonyWednesday 30 September 2026, 19:52 UTC (12:52 Pacific)Follows Proposed next steps for October 2026

If you are an agent starting work on the production system, read this first. Then read notes 15 to 18 for the history, status, direction and plan. Anthony's time and judgment are the scarcest inputs here. Most useful work does not need them. This note sorts one kind from the other.

The short version

  • Trust the file, not the report. Measure the audio you actually wrote.
  • Calibrate every measure against a known answer before using it.
  • Commit everything that works, the same day. Untracked work has been left behind twice.
  • Most of the ladder's lower rungs need no human feedback. Build those.
  • Only taste needs Anthony. Make each question to him cheap and informative.

What the record teaches

Each lesson below cost at least one session to learn. Each has a source in the repos or notes.

Check the output, not the report

A render can report success and be silent. This week found four separate causes. There was no audio device. Source tracks were armed. "Back to Arrangement" was lit. Samples were missing.

A tool also reported a 3.7-second file that was 6.7 seconds long. A tight loop polling meters once left the control channel stuck. The rule is simple. Open the file and measure its peak before you believe anything.

Every ruler bends on real audio

The research found three bent measures in three days. Decay read pitch. The pump measure saturated near 12 dB. The listening test used sounds that real tracks never make.

This week ears had a mislabelled peak and fake embeddings. None of these showed up on synthetic tests alone. Build a known-answer case first. Then gather data.

Commit or lose it

The sweep scripts, a better recorder and a Hammerspoon rewrite were never committed. When the rig moved to a new Mac, it was rebuilt from March code. The same bugs were found again.

Commit working code the day it works. Push it to GitHub. Keep big audio in cloud storage, not git.

Live's API has hard edges

The Live API cannot export audio. It cannot cut or delete time either. Record through a resampling track instead. Edit time through the Edit menu, which moves automation too.

Never read a value in the same call that wrote it. That can crash Live. Keep each call under about twelve seconds and twenty parameters. The hands skill lists the rest.

Knob labels are not behaviour

A knob's name does not tell you what it does to the sound. Decapitator's Drive does not raise crest steadily. It rises, then falls. Roar was switched off in the real set. The compressor never engaged at the set's threshold.

Read the set before you sweep it. Then sweep, and write down what you measured.

Protect the originals and the person

Work on a copy of the whole project, never the original. Never press a destructive button in a dialog. Answer with the safe one.

Screenshots fill context fast. One session passed a million tokens on full-size captures. Prefer text from the control channel. Crop images when you must use them.

Ask Anthony before taking screenshots or taking over his screen. He has said so directly.

Date from the record

One task was once given a year and took a day. Another took two days where the first result came in thirty minutes. Date new work from similar past work in the commit log.

External services fail too. A Cloudflare incident this week delayed a deploy for hours. Check the status page before debugging your own code.

Every finished row gets a dated note on this site the same day. That rule already exists. It lapsed for two weeks in September.

What learning is possible without him

The corpus holds 508 tracks from 317 producers. Genre facts can be learned from it alone. How often clap lands on two and four is one. Where kicks sit in pitch is another.

Device behaviour can be learned by sweeping. That covers every installed plugin and every Live device. It needs compute and a working rig, not taste.

The rig itself can be learned. Which failures happen, how often, and how long renders take. That record makes future dates honest.

What cannot be learned alone is which of two good versions he prefers. No amount of corpus data answers that. Do not pretend it can.

What not to do without him

  • Decide what sounds better. Offer choices instead.
  • Save, move or delete his originals. Work on copies.
  • Publish anything to this site without his yes, except dated notes about results.
  • Install background jobs or change system settings. Ask.
  • Sign into his accounts or activate plugins. Those are his.
  • Put the old phone server online. It is unsafe on a network.
  • Get around a refused permission. Report it and let him decide.

Where to start

Run the startup script in the hands repo. Check the audio clock and the Live set. Read the hands skill end to end. Then take the first unfinished row in the table above.

Terms are defined in the glossaries of note 15 and note 10. New here: a known-answer case is a test signal with a known true value. A preflight is a set of checks run before a render starts.
