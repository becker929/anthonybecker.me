Big builds in one write

A build in artworld costs one record per chunk it covers. This RFC proposes one record for the whole build instead. Small builds carry their voxels inside that record. Large ones point at a blob, a file in the builder's own Bluesky repo. A dry run exists today. Nothing is live.

Written by Claude Opus 5.5Addressed to Anthony, and to agents building in artworldWednesday 21 October 2026, 07:00 UTC (00:00 Pacific)Draft

Summary

  • Add a record type called a volume. It names a box of chunks and fills up to 128 of them.
  • It holds every chunk in the box, compressed into one run of bytes.
  • Up to 64 KB, the bytes sit inside the record. Larger ones go in a blob the record points at.
  • A builder writes the volume once. Today the Black Pyramid took 164 record writes.
  • The world server checks the volume and fans it out to the regions.
  • Small edits still use chunk records. A chunk record always wins over a volume.

The problem

The world is cut into chunks, each 32 voxels on a side. Every chunk a friend builds in is one record in their repo. A record can already hold a whole chunk: 32,768 voxels in one write. So one write is not small. The cost is the number of chunks a build covers.

The Black Pyramid shows it. It covers 100 chunks and holds 130,052 voxels. It took 100 claims and then 64 paints. That ran for two minutes and 22 seconds. It also spent 428 of the owner's 5,000 hourly Bluesky points.

The info signs along the world's edge are slow for the same reason. Each covers 12 chunks and took about 30 seconds. Each claim waits for the world to confirm it. Then each chunk is written a second time with its content.

Why batching does not help

Bluesky lets a client send many record writes in one call, called applyWrites. But its rate limits count each record, not each call. A create costs 3 points, an update 2, a delete 1. So a batch of 100 creates costs the same 300 points as 100 single calls. It saves round trips, not quota.

The fix has to cut the number of records. One record per build is the floor.

The proposal

Bluesky repos hold two kinds of data. Records are small structured objects that travel on the network's event stream. Blobs are uploaded files that a record points to. Images on posts are blobs. A volume can use either.

Inline is the default. The bytes ride in the record, so the world server gets them with the event. Nothing extra is fetched, and nothing can go missing. Most builds fit: big single-colour areas compress to almost nothing. A blob is the fallback for builds too detailed to fit. Both carry the same bytes.

The record

The bytes

The bytes list the chunks in the box in a fixed order. Each chunk is one of four kinds. The whole list is then compressed with deflate.

"AWV1"               magic, 4 bytes
nx ny nz             box size in chunks, 1 byte each
per chunk (x fastest, then z, then y):
  kind               0 skip, 1 empty, 2 solid, 3 data
  solid: colour      1 byte
  data:  length      varint, then the chunk in rle1
  • Skip. Not part of the build. An L-shaped build can use a box without claiming the gap.
  • Empty. Claimed and cleared.
  • Solid. Claimed and filled with one colour. Two bytes for 32,768 voxels.
  • Data. The chunk in rle1, the same run-length code chunk records already use.

The world server refuses bytes with a wrong header or an out-of-range size. It also refuses one with too many chunks, a broken run, or bytes left over. It stops inflating once the output passes the largest legal size. That defeats a small file built to expand without end.

Who owns what

  • Every chunk in the box that is not skipped becomes the builder's plot. Each one counts against the plot limit.
  • It is all or nothing. One chunk in the shared zone, or owned by someone else, refuses the whole volume.
  • A half-placed build would be worse than none. The builder could not tell what landed.
  • As with chunks, the first valid claim to reach the world wins.

Editing a volume

The rule is simple: per chunk, the owner's chunk record beats the owner's volume. The existing paint tools then work unchanged. Painting a chunk of a volume writes a chunk record. It starts from the volume's content there. Deleting that chunk record shows the volume again.

Replacing the volume changes every chunk that no chunk record covers. Deleting the volume frees and clears those same chunks.

How the world takes it in

  1. The record arrives on Jetstream, Bluesky's event stream. Inline bytes come with it; a blob does not.
  2. The world server checks the record, the box, ownership and the plot limit.
  3. For a blob, it fetches the file from the builder's own server, with getBlob. It checks the bytes against the blob's hash.
  4. It decodes the bytes within the size limits. It checks every chunk against the mesh budget. One failure refuses the whole volume.
  5. It sends each region its chunks as one batch. Chunk records use the same path.
  6. A region that fails is retried. The volume stays pending until every region has it.

Risks and open questions

  • Edits are coarse. Changing one voxel of a volume means a new blob. Small edits should use chunk records instead.
  • Blobs vanish. A Bluesky server deletes a blob as soon as no record points at it. So undo cannot point back at an old blob. It rebuilds the old content from the world's history and uploads it again. Inline volumes avoid this.
  • Fetching costs. Each blob volume is one extra request to the builder's server. Backfill fetches every blob again.
  • Event size. Inline bytes ride on the network's event stream to every listener. That is why inline stops at 64 KB, the cap chunk records already use.
  • Server time. Checking 128 chunks against the mesh budget is real work. The dry run measures it before any limit is fixed.
  • Moderation. One write can now change a large area. Hiding a volume must hide all of it at once.
  • Not in version one. Animated volumes, volumes in the shared zone, and boxes over 128 chunks.

The dry run

Agents in artworld get a new tool, place_volume. It takes the same boxes and voxels as paint, in world coordinates. Today it only accepts dry_run: true. It writes nothing to any repo and changes nothing in the world.

It does everything else a real volume would need.

  • It works out the box and each chunk's content, starting from what is there now.
  • It checks ownership, the shared zone, the world's edge and the plot limit.
  • It checks every chunk against the mesh budget and the voxel budget.
  • It encodes the bytes, then decodes them with the world server's decoder. Both copies must match.
  • It reports chunks by kind, claims needed, voxels changed, size, and inline or blob.
  • It reports the time each step took, and Bluesky points for both paths.

Path to live

  1. Run the dry run on real builds and fix the limits from its timings.
  2. Publish the volume lexicon.
  3. Teach ingest to fetch, check and apply volumes, with backfill and retry.
  4. Turn on writes in place_volume: create the record, uploading a blob first when needed.
  5. Move info signs and large admin builds onto volumes.

Each step is its own change, tested on staging before production.

Glossary

applyWrites
A Bluesky call that sends several record writes at once. Each write still costs its own points.
Backfill
Reading a friend's whole repo again to rebuild their part of the world. Used after an outage.
Blob
A file uploaded to a Bluesky repo and named by its hash. A record points at it. It does not travel on the event stream.
Chunk
A cube of the world 32 voxels on a side. Each one is a possible plot.
Chunk record
A record holding one chunk's voxels. Writing one claims that chunk.
Deflate
A common compression method. Large single-colour areas shrink to almost nothing.
Ingest
The world server's step that reads new records from the event stream and applies them.
Inline
Carried inside the record itself, rather than in a separate file.
Jetstream
Bluesky's stream of repo changes, filtered to the record types a service asks for.
Mesh budget
The most drawing data one chunk may turn into. It keeps phones from choking on noisy patterns.
PDS
Personal data server: the server that holds a person's Bluesky repo.
Plot
A chunk owned by one friend. Only its owner can change it.
Points
Bluesky's write rate limit. Each account gets 5,000 an hour and 35,000 a day.
Record
A small structured object in a Bluesky repo. Posts, likes and chunks are records.
Region
A 16 by 16 column of chunks, run by one server process.
rle1
artworld's run-length code: a count, then a colour, repeated.
Shared zone
The plaza in the middle of the world. Nobody can claim it; everyone places small pieces there.
Volume
The proposed record: a box of chunks, with their voxels in one blob.
Voxel
One coloured cube, the world's smallest unit.
