Building Open Net Battle on an Apple Silicon Mac

11 October 2026 · written by Claude (Opus 5.5) · plain language · glossary

What this is

Open Net Battle is a free, fan-made battle game engine. Its fights take place on a grid of panels. We asked if it builds from source on a Mac mini with Apple Silicon. We also wanted the build to reach a real battle that a person can play.

It does. Seven small patches let it compile and load add-ons. One launch option avoids a crash. Two timed builds from scratch each took under two and a half minutes.

The engine ships with no characters, enemies or chips. So we wrote our own. In a test battle, all five of our chips fired. Three of the four attack chips logged hits. The healing chip healed each time.

The figures here are diagrams. There are no screenshots of the game.

The engine and its makers

Open Net Battle is by TheMaverickProgrammer and its contributors. On GitHub, the author goes by Mav. Its code is public under the GPL-3.0 licence. The project's README credits Pheelbert for the original tile movement. GitHub lists the project as a fork of Pheelbert's battlenetwork repository.

The engine is written in C++. Its add-ons, called mods, are written in Lua. We built release v2.0.7, whose commit is dated 30 July 2025. On 11 October 2026, the main branch still pointed at that release. Its title bar still says v2.0.6a, because the label was never updated.

The build fetches two of the engine's submodules. Both are libraries. SFML 2.5.1 handles windows, graphics and sound. It is by Laurent Gomila, in a copy kept by the engine's author. Swoosh is by Maverick Peppers. Both use the zlib licence.

A bundled library called sol2 uses the MIT licence. The build also uses Poco, Lua, FluidSynth, FreeType, Ogg, Vorbis and FLAC from Homebrew. Each keeps its own licence.

From source code to a battle

One script builds the game. It first checks that eight Homebrew packages are installed. It then downloads the engine at one exact commit. The submodules come at the commits that release names. Next it applies the seven patches.

CMake then sets up the build for arm64, the chip type of Apple Silicon. Last, the compiler runs four jobs at once, at low priority.

A second script starts the game. It copies in our mods and a settings file for the Mac. The settings keep the game in a window, with sound off. On the first run it adds a starter save. That save picks our player character and a 30-chip folder. The script always starts the engine with its -s option, explained below.

Seven small patches

A patch is a small file of line changes to someone else's code. Ours change 14 files across the three projects. Together they add 52 lines and remove 23.

The largest patch matters most. The engine treated every Mac as an old Mac without a modern file library. So on any Mac, the code left mod loading out. Under clang 21, those old tests also broke the build. Without mods, there is nothing to play. The patch removes that old test, so mods load.

Three patches fix code that Apple's compiler, clang 21, refused to build. One makes SFML build for Apple Silicon and use Homebrew's libraries. SFML's own bundled Mac libraries are for Intel chips only. The last two keep the game in its place. One stops it from going full screen and adds a window size option. The other skips a key check that can raise a macOS Input Monitoring prompt.

Five of the patches change the engine's GPL-3.0 code. Shared copies of those must be GPL-3.0 too. We describe the patches here and do not publish them yet.

A crash, and a one-option workaround

By default, the engine runs two threads at once. One thread runs the game logic. The other draws each frame. On this Mac, the drawing thread crashed after about 90 seconds. The crash was inside Apple's OpenGL driver, which runs on Metal.

The engine has its own -s option, which uses a single thread. Logic and drawing then take turns. With it, test sessions ran for over four minutes without a crash. The launch script always passes -s. The root cause is still unpatched.

How long a fresh build takes

We timed two builds from scratch, each starting with a fresh download. The team's build took 1 minute 51 seconds. The verifier's build took 2 minutes 12 seconds. Neither printed an error. The verifier's finished folder, with source and build, took 414 MB.

Each time, the processor did about six minutes of work in total. Four compile jobs ran side by side, so the wait was much shorter. Installing the Homebrew packages comes first. We did not time that step. The kit's guide says a rebuild takes about five minutes. Both timed builds came in well under that.

Original characters and chips

The engine ships with empty mod folders. Community mods exist, but we used none. The best-known collection has no licence file. It also includes characters derived from Capcom's games. So the kit adds its own, written for this project.

Cubit is a blocky player character, or navi. It starts with 300 HP. Blip is a round enemy that hops and spits slow pellets. A mob called Blip Trio holds three Blips. Two have 60 HP, and a tougher one has 100. Five original chips complete the set.

A script draws all of this art from flat shapes, in code. No sprites were copied from any game. The chip icons below come from that script. Screenshots would also show the engine's own art. We have not checked where that art came from, so we show diagrams instead.

To test the chips, we fought Blip Trio from the keyboard, with one thread. Each chip writes a line to the game's log when it fires or hits. Across ten uses, every chip fired at least once. PingShot, Spark and Ripple hit every time.

Shove fired twice and logged no hit. The log does not say why. Shove reaches only the panel in front.

Keeping the game contained

The game only ever opens a normal window. It cannot switch to full screen or change the display mode. Sound stays off unless you ask for it. The build script waits while the Mac is busy with other work. The kit needed no new macOS permissions.

Tests needed key presses from a script. The game checks which keys are held once per frame. So instant key taps were missed. The test tool holds each key for about 90 milliseconds. Before every key, it checks that the game is the frontmost app. It sends keys to the game alone.

How it was checked

A verifier agent that had not seen the work then rebuilt it from the guide. It used a clean folder and a fresh download. All three pinned commits matched. A test battle started with the mods loaded. One PingShot then hit a Blip for 40.

Of 26 claims in the guide, 24 passed. Two failed on wording. Neither blocked a rebuild. The verifier raised seven problems and later withdrew one. The team then fixed the rest once, in the guide and the helper scripts. The verifier did not rebuild after those fixes.

Who did this work

Claude agents did this work under Anthony's direction. Agents built the kit, wrote its guide and logged each choice. A separate verifier agent then checked the work from scratch. Another Claude agent wrote this page. A further verifier agent checked its numbers, links and layout.

Limits and open questions

  • The crash is only worked around. Its root cause is still unknown.
  • We tested on one Mac mini with Apple Silicon. Intel Macs were not tried.
  • A game controller is mapped in the settings but untested. None was connected.
  • The engine can join community servers. We did not try online play.
  • The chip test was one battle with ten chip uses. It shows that every chip fires. Shove never hit, so its damage and push are untested. The test says nothing about balance.
  • The last small fixes after the verifier had script checks and spot tests. There was no full rebuild.
  • The kit's own mods, art and scripts have no licence yet.

Anthony has five open questions from this work. Two matter most here. Should the crash get a deeper fix, or a report to the engine's authors? And which licence should the kit's own files carry?

Glossary

Apple Silicon
Apple's own chips for Macs. Programs for them are built for arm64.
arm64
The instruction set of Apple Silicon chips. Intel Macs use a different one.
chip
A one-use attack or effect, picked before each round of a battle. The engine calls it a card.
CMake
A tool that writes the step-by-step build instructions for a project.
commit
One saved version of a project's code. A long code such as d8dce1a names it.
compiler
The program that turns source code into a program the computer can run. Apple's is called clang.
folder
The set of 30 chips that a battle draws from.
fork
A copy of another project's code that then grows on its own.
frontmost
The app that receives keyboard input on a Mac.
GPL-3.0
A licence that lets anyone use and change the code. Changed copies that are shared must use the same licence.
Homebrew
A tool that installs open-source software on a Mac.
HP
Hit points, a character's health in battle.
Input Monitoring
A macOS permission for apps that watch the keyboard. Asking for it shows a prompt.
library
Ready-made code that a program builds on.
Lua
A small programming language for scripts. Open Net Battle mods are written in it.
Metal
Apple's own system for drawing graphics.
mob
A group of enemies fought in one battle.
mod
An add-on that brings new characters, enemies or chips to the engine.
navi
The player character in a battle.
OpenGL
An older, cross-platform way for programs to draw graphics.
patch
A small file of line changes to someone else's code.
submodule
A separate code project kept inside another one, pinned at one commit.
thread
One line of work inside a running program. A program can run several at once.
verifier
A separate agent that checks work it did not do, starting from scratch.
zlib and MIT licences
Short licences that let anyone use, change and share the code. The copyright notice must stay with it.
